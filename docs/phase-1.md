# Filemux 阶段一实现说明

## 1. 用途与执行范围

本文记录用户已经确定的需求、基本验收条件及实施建议，供 goal 在新会话中读取。`docs/progress.md` 记录实际进度、验证结果及下一步。

- 目标是完成可运行的阶段一产品，不是仅交付 workspace、协议占位接口或 GUI 演示。
- 确定需求不能为了通过测试而删减。实现建议可以根据所选依赖和实际代码调整，必要决定简要记入进度文档。
- 不需要目标板卡，不以 U-Boot 真机、完整 Linux 无盘启动或严格故障测试作为交付前提。
- 在当前工作区实施，保留已有改动；未经用户授权不创建 worktree，不提交、推送、切换分支或改写历史，不执行系统级安装及生产环境变更。
- 默认自主推进工具和项目资料能够回答的问题。只有必须由用户决定或授权的事项才提问；遇到真实外部阻塞时记录原因并继续其他可执行工作，不能把阻塞项标为完成。

## 2. 已确定的需求

### 2.1 项目与平台

- 使用 Rust，采用 Cargo workspace，仅保留 `filemux-core`、`filemux-cli`、`filemux-gui` 三个 crate。
- 支持 Windows、Linux、macOS。平台差异通过对应实现处理，不依赖宿主机的内核 NFS 服务端。
- 同时提供 CLI 和原生桌面 GUI；GUI 使用 egui，推荐使用 eframe。
- CLI 和 GUI 复用同一套服务与配置逻辑，不能各自维护协议实现。
- 优先面向可信局域网，目标用途是 U-Boot 文件加载和 Linux 无盘启动相关文件访问；不宣称已通过未执行的设备或启动兼容测试。

### 2.2 协议行为

| 协议 | 阶段一必须实现 |
| --- | --- |
| TFTP | 文件下载与上传；上传默认关闭，开启后才能接收上传；默认不覆盖已有文件。 |
| HTTP | 只读文件下载、基本目录浏览、GET、HEAD、基本 Range 请求；拒绝修改文件的请求。 |
| NFSv3 | 只读，支持 UDP 与 TCP；提供 MOUNT v3 及必要的 portmapper 发现；支持挂载所需的属性查询、路径查找、目录读取和文件读取；各修改入口按协议返回适当错误。 |

- 配置应能选择共享目录、监听地址、端口、协议启用状态及 TFTP 上传开关。
- 三种协议对同一共享的文件访问规则应一致，但 HTTP、NFS 的只读限制不能随 TFTP 上传开关改变。
- TFTP 未完成的上传不能以成功文件对外发布；失败不得被报告为成功。
- 不要求实现所有可选协议扩展。实际支持的传输模式、选项、锁行为及限制应写入使用说明；不支持的行为不能伪装为成功。

### 2.3 NFS 跨重启恢复

服务重启后，已挂载客户端不需要重新挂载即可继续访问，前提是共享身份、持久状态及对应文件系统对象没有被删除或替换。

- 共享身份、对象身份及解释旧文件句柄所需的信息必须能够跨进程重启恢复。
- 不能使用每次启动重新生成的编号或启动时间，让所有旧句柄失效。
- 不能把路径哈希作为唯一对象身份；同一路径删除后重建，旧句柄不能错误地访问新对象。
- 仅固定 generation 不等于已实现恢复，还必须恢复对应对象映射。
- 需要新增持久信息时，信息持久化完成后才能向客户端返回依赖它的句柄。
- 状态丢失、损坏或与导出内容不匹配时明确报错，不静默重建并声称恢复成功。
- 服务器停机期间允许客户端访问等待；本需求不要求零中断，也不要求删除或替换对象后的旧句柄仍有效。

### 2.4 文件系统语义与安全

- 文件访问必须限制在批准的共享范围内，处理路径越界、绝对路径及平台特有路径形式。
- 不仅靠分离的路径检查和再次按路径打开来防止链接替换造成越界。
- NFS 应正确处理文件、目录及符号链接的相关协议语义，保留启动文件所需的执行权限等信息；不能把所有对象伪装成普通文件。
- 返回 NFS 符号链接内容与在宿主机上跟随链接是两回事；不能因此读取共享范围外的宿主机文件。
- 不能通过请求的文件类型或元数据去打开宿主机设备执行 I/O。
- Windows 与 Unix 元数据不同，采用的映射和限制必须明确记录，不能宣称完整等价。
- 文件传输使用流式或定位读取，不因传输大文件而整文件载入内存。传输任务、缓冲及事件队列应有明确限制。
- 默认使用保守的网络访问设置，并在使用说明中明确：TFTP 和采用 AUTH_SYS 的 NFS 不提供可信用户认证与传输加密。

### 2.5 CLI 与 GUI

- CLI 至少能检查配置、前台启动已配置服务、输出可理解的错误，并正常退出和释放资源。
- GUI 至少能配置共享与网络参数、启停服务、显示真实运行状态及基本访问和错误记录。
- 启动成功必须以实际监听成功为准。某项服务启动失败应显示对应原因，不能显示为运行中。
- 区分编辑中的配置、已保存配置与正在使用的配置。第一阶段可以采用重启服务后使用新配置，不要求复杂热更新。
- GUI 不能在绘制函数中执行阻塞网络或文件操作；关闭 GUI 时应明确处理其内部服务，不假装存在另一个后台守护进程。
- GUI 支持正常中文显示及基本缩放；界面文字使用自然、准确的简体中文。

### 2.6 GUI 预览的先后要求

在 GUI 页面、组件拆解和界面开发之前，必须：

1. 调用 `generate_image` 生成 GUI 预览图，不能用文字描述、自绘草图或占位图片代替该工具。
2. 将生成结果保存到 `docs/previews/`，并在进度文档中记录实际路径。
3. 检查关键中文、功能表达以及 egui 实现可行性，再据此进行页面与组件拆解及开发。

用户没有要求生成后必须等待人工批准；没有需要用户决定的问题时可在检查后继续。若工具确实不可用或生成失败，记录实际原因，继续后端等不依赖预览的工作，但不能跳过这一要求开始 GUI 实现。

## 3. 建议实现方式，不是额外功能要求

### 3.1 Workspace 职责

按用户确认的三个 crate 划分；协议、文件系统和服务管理作为 core 内部模块，不再拆成独立 crate。

| Crate | 职责 |
| --- | --- |
| `filemux-core` | 配置、受限文件访问、持久身份、上传发布、HTTP/TFTP/NFSv3、服务启停及事件；按 `fs`、`http`、`tftp`、`nfs`、`engine` 模块组织。 |
| `filemux-cli` | 命令入口、配置加载和终端输出，依赖 core。 |
| `filemux-gui` | egui 桌面界面及字体资源，依赖 core，可独立打包发布。 |

CLI 单独构建不应强制依赖窗口和 GPU 组件。推荐统一 workspace 依赖、固定工具链，并随项目交付 Cargo.lock；这不授权执行 Git 提交。

### 3.2 依赖与存储建议

- 异步运行时推荐 Tokio；HTTP 推荐 axum、tower-http；CLI 推荐 clap；GUI 推荐 egui、eframe。
- `async-tftp`、`nfs3_server` 是调研候选，不是必须采用或已经验证的选型。复用成熟实现优先于重写，但实际接口必须满足需求。
- 调研时 `nfs3_server` 主要公开 TCP 监听入口，RPC 分发是内部模块；若采用它，UDP 可能需要受控源码修改，不能假定增加一个 UDP socket 就已完成。
- 调研时 `async-tftp` 的上传路径存在先 ACK 再写入的源码风险；采用时核对所选版本及上传成功语义。这是待验证风险，不是本项目已经复现的失败。
- 持久状态推荐 SQLite，但没有强制数据库、表结构或 ORM 要求。
- 保留 POSIX 元数据的 rootfs 快照、tar 导入是实现建议，不是已确认的独立交付功能。不要预先实现多种镜像格式；若为满足明确需求确有必要，采用最小方案并记录原因。
- 不搭建通用插件、云存储或任意文件系统框架。

### 3.3 建议实施顺序

1. 建立 workspace，确定共享、文件访问与持久身份的最小接口。
2. 优先解决 NFS UDP/TCP、基本读取及跨进程重启句柄恢复，再完善三协议及 CLI。
3. 完成真实服务的本机基本集成测试。
4. 生成并检查 GUI 预览，再拆解和实现 egui GUI。
5. 完成基本界面运行检查、使用说明及最终验证。

这是同一个阶段内的里程碑，不是允许只完成前几项就结束目标。

## 4. 基本验证标准

用户只要求基本单元测试与集成测试，不要求建立专用硬件或启动实验室。

| 范围 | 基本验收 |
| --- | --- |
| 单元测试 | 配置解析、上传开关与只读策略、路径限制、句柄编码及持久恢复等实际行为。 |
| HTTP 集成测试 | 启动真实服务；GET 下载内容正确、HEAD 无响应体、基本 Range 正确、修改请求被拒绝。 |
| TFTP 集成测试 | 启动真实服务；下载正确、默认拒绝上传、开启后上传成功且内容一致。 |
| NFS 集成测试 | 启动真实服务；UDP/TCP 的基本 MOUNT、LOOKUP、READ、READDIR 调用及修改请求拒绝。 |
| 重启恢复集成测试 | 使用临时目录和持久状态启动服务，取得文件与目录句柄；结束服务进程并重新启动后，直接用旧句柄查询或读取，内容正确。不通过重新 MOUNT/LOOKUP 获取替代句柄来绕过验证。 |
| CLI 基本运行 | 用实际配置启动并发起本机请求，正常退出后资源可释放。可与集成测试合并，避免重复搭建验证。 |
| GUI 基本运行 | 实际打开窗口，检查中文、基本配置、服务启停和状态显示；不要求自动截图比对。 |
| 平台 | 做好三平台实现和 CI 构建、测试配置；实际运行过的平台和结果如实记录，未执行的检查不能记为通过。 |

- 测试使用临时目录、空闲高端口和本机网络，不依赖系统 NFS 挂载、管理员权限、目标板卡或外部服务。
- 单元测试验证行为与边界；集成测试通过协议访问真实服务，不以 mock 或服务端自造结果代替。
- 保留必要、确定且相互隔离的测试；不为覆盖率数字堆砌测试或搭建额外框架。
- 最终至少执行 `cargo fmt --all -- --check` 与 `cargo test --workspace`，并记录实际结果。按代码变化集中运行相关检查，不在未发生变化时反复重跑。

## 5. 非交付门槛与非目标

以下内容不作为阶段一交付前提：

- 目标板卡、U-Boot 真机矩阵、完整 Linux 无盘启动及 QEMU 启动环境。
- 系统断电、复杂网络故障注入、大规模并发、性能压测和长时间稳定性测试。
- 公网部署、账户体系、Kerberos、完整 NLM/statd 锁恢复或所有客户端默认参数兼容承诺。
- NFSv2、NFSv4、HTTP/NFS 写入、DHCP/PXE 调度、远程控制 API、系统服务安装及自动更新。
- 多种 rootfs 镜像解析、云存储、插件机制及与本阶段行为无关的额外功能。

不要求这些验收，不代表可以把必须实现的协议行为写成占位代码，或宣称未验证的设备兼容性。

## 6. 完成条件

只有同时满足以下条件，才能报告阶段一完成：

1. workspace、CLI、GUI 和三种真实协议服务均可使用，而非仅可编译的骨架。
2. TFTP 上传默认关闭，HTTP/NFS 只读，NFS UDP/TCP 与跨进程重启句柄恢复满足上述基本验收。
3. GUI 的 generate_image 预览先于 GUI 拆解与开发，并有实际生成文件。
4. 基本单元测试、集成测试及本机运行检查已执行；不能通过删除必要验收、skip 或 mock 让结果变绿。
5. README 包含 CLI/GUI 启动方式、配置示例、端口与权限说明、支持范围、NFS 客户端必要选项及已知限制。若采用只读 NFS root，说明客户端运行时写入应由 tmpfs/OverlayFS 等解决；不需要为此额外制作完整客户端系统。
6. 进度文档记录实际命令、结果、运行平台和未验证内容；只清理本任务产生的可丢弃临时产物，停止本任务不再需要的进程。
